== Purpose and Scope

Companion to `CRG-AUDIT-2026-04-18.adoc` in this same directory. The audit
demoted `academic-workflow-suite` from a self-declared *B* to an audited
*D (Alpha, with structural-policy debt)* — a two-grade overclaim. STATE.a2ml
at `.machine_readable/6a2/STATE.a2ml` has been updated to record the
demotion.

This document is the honest remediation path from *D back to C*. It is
*not* a plan to reach B. B requires 6+ diverse external targets and an
issues-fed-back log that do not exist for this repo today; chasing B
before earning C is how the overclaim happened in the first place. Once C
is cleanly audited and held for a quarter of real use, a separate C→B
plan can be written — not before.

Target audience: whoever does the D→C work (likely the same author).

=== Guiding principle

*Holding at D honestly is better than racing to C dishonestly.* The grade
is an artefact of the evidence, not of effort spent. A D that records
"structural-policy debt cleared, dogfooding evidence still thin" is a
*more useful* artefact than a C stamped on the same repo without the
evidence to back it.

== Phase Overview

.Phase summary — D floor to C earn
[cols="1,3,1,1"]
|===
| Phase | Goal | Cost | Dependency

| 0 | Stabilise the D floor (structural-policy debt) | M | none
| 1 | Annotation depth (READMEs + docstrings) | L | Phase 0 complete
| 2 | Dogfooding evidence (STATE section + DOGFOOD-LOG) | M | Phase 0 complete
| 3 | Behavioural test matrix (PASS counts + completion lift) | XL | Phase 0 complete
| 4 | CI green + proof freshness | S | Phases 0-3 complete
| 5 | C audit re-read | S | All above complete
|===

*Cost scale*: S = <1 effort-day, M = 1-3 effort-days, L = 3-7 effort-days,
XL = >7 effort-days. Effort-days are calendar days of focused work by one
person, not wall-clock time.

*Biggest rock*: Phase 3 (XL). Everything else is discipline work; Phase 3
is where real engineering happens — making the backend and office-addin
test suites actually run, and demonstrating behavioural coverage rather
than build-success coverage.

== Phase 0 — Stabilise the D Floor

*Goal*: Remove structural-policy violations so the D grade is cleanly met
rather than being "D with structural-policy debt".

*Dependency*: None. Start here.

*Cost*: M (1-3 days).

*Exit criteria*:

- `Containerfiles/` contains only `Containerfile.*` (no `Dockerfile.*`)
- Compose files at root renamed (or consolidated) to `compose*.yml` /
  `podman-compose*.yml`
- `components/office-addin/` has no `package.json` and no `webpack.config.js`
  at the top of the tree (Deno migration path documented if not yet complete)
- `mix test` runs inside `components/backend/` and produces a PASS/FAIL tally
  captured in a dated build log under `docs/practice/`
- `docs/READINESS.md` exists, populated from `rsr-template-repo/READINESS.md`
- AI-jail test file has a CUDA-optional skip-path: test code detects CUDA
  absence and exits cleanly, rather than the whole suite being marked BLOCKED

*Tasks*:

* [ ] Rename `Containerfiles/Dockerfile.backend` → `Containerfile.backend`
* [ ] Rename `Containerfiles/Dockerfile.core` → `Containerfile.core`
* [ ] Rename `Containerfiles/Dockerfile.nginx` → `Containerfile.nginx`
* [ ] Update all `docker build -f` / CI references to the new names
* [ ] Rename `docker-compose.yml` → `compose.yml`; propagate to
  `compose.dev.yml`, `compose.prod.yml`, `compose.test.yml`
* [ ] Update Justfile recipes that invoke `docker-compose` to use
  `podman compose` and the new filenames
* [ ] Inventory `components/office-addin/` for Node/npm/webpack usage;
  write a `MIGRATION-DENO.adoc` in that subtree with the concrete port
  plan (no code change required in Phase 0 — *document then deprecate*)

*Anti-patterns to watch for in Phase 0*:

  rewriting backend code "while we're in there". Record new ideas in
  STATE.a2ml and move on.

  success is a weaker claim than useful content.

== Phase 2 — Dogfooding Evidence

*Goal*: Tie the suite to real academic workflow use with dated, verifiable
log entries. "Could be dogfooded" is not dogfooding; only a concrete log
entry counts.

*Dependency*: Phase 0 complete (need working builds before real use).

*Cost*: M (1-3 days of setup + ongoing organic use).

*Exit criteria*:

- STATE.a2ml contains a `[dogfooding-status]` section populated with at
  least 3 concrete "done — <evidence>" entries, each naming a real
  assignment, paper, module, or workflow and a date
- `docs/practice/DOGFOOD-LOG.adoc` exists and has at least 4 dated entries
  over at least 4 weeks (weekly rhythm minimum)
- At least one Office add-in deployment recorded against a real OU tutor-
  marked-assignment (TMA) workflow — or, if that's not realistic yet, a
  documented *in-progress* TMA tie-in with named blocker
- At least one CLI invocation recorded against a real document-management
  task (not a synthetic example)

*Tasks*:

* [ ] Create `docs/practice/DOGFOOD-LOG.adoc` with the template from
  `rsr-template-repo/docs/practice/DOGFOOD-LOG.adoc` (or equivalent)
* [ ] Add `[dogfooding-status]` section to
  `.machine_readable/6a2/STATE.a2ml` with keys: `cli-used-on`,
  `backend-deployed-to`, `office-addin-loaded-in`,
  `ai-jail-run-against`
* [ ] First log entry: whatever workflow triggered this audit cycle
  itself — using the CLI to audit or format this very repo counts
* [ ] Maintain weekly cadence for at least 4 weeks before claiming C
* [ ] Cross-link DOGFOOD-LOG entries from the relevant component README

*Anti-patterns to watch for in Phase 2*:

- *"Backdate log entries to hit the bar"* — fatal. A dated entry must
  correspond to an event that actually happened on that date. If this is
  hard, say out loud that the suite hasn't been used in anger yet — that
  is honest D-held behaviour.
- *"Dogfooding = `cargo test` passes on my laptop"* — no. Dogfooding
  means the tool did a job that needed doing, and you would have been
  mildly annoyed if it hadn't worked.

== Phase 3 — Behavioural Test Matrix

*Goal*: Raise `completion-percentage` from 42 to at least ~80, backed by
*behavioural* tests (the suite does the thing it claims), not *structural*
tests (the code compiles).

*Dependency*: Phase 0 complete (backend tests must actually run).

*Cost*: XL (>7 days). This is the largest rock in the plan.

*Exit criteria*:

- `components/backend/` `mix test` reports all tests PASS, with a total
  count recorded in STATE.a2ml's `[test-matrix]` section
- `components/office-addin/` ReScript tests report all PASS, with total
  count recorded
- AI-jail suite either runs (if CUDA available) or cleanly skips (if not),
  with BLOCKED status removed from STATE.a2ml
- At least one *behavioural* e2e test per component that exercises the
  real workflow (Office add-in loads a document → Moodle auth round-trip
  → TMA submission happy-path → CLI processes result)
- `completion-percentage` recalculated honestly against the phase-3 exit
  criteria, not against build success. Expected landing zone: 70-85.

*Tasks*:

* [ ] Enumerate backend test files; for each that "pending mix run"
  references, run it and record output. File:
  `docs/practice/BACKEND-TEST-MATRIX-2026-04-18.adoc`
* [ ] For each backend test that fails, either fix the production code
  or document the test as aspirational and remove it from the count
* [ ] Run ReScript tests in `components/office-addin/` — these are
  claimed as "Types (15) + BackendClient (18) + OfficeAPI (22)
  implemented" with no PASS count. Convert to a PASS count.
* [ ] Add a behavioural e2e test that covers: document-open →
  add-in-auth → backend-reply → CLI-postprocess. Even one real e2e
  beats ten unit tests for the C bar.
* [ ] Replace any `.unwrap()` panics discovered during this phase with
  proper `Result` returns. Do *not* replace with `.expect("TODO")`.
* [ ] Run `panic-attack assail` across the Rust crates; classify any
  `unsafe_blocks` hits as (a) banned partial casts, (b) legitimate FFI,
  or (c) legacy to remediate
* [ ] Recompute `completion-percentage` per the standard and record the
  derivation in the same file that reports the number

*Anti-patterns to watch for in Phase 3*:

- *"Completion = `dune build` / `cargo check` passes"* — categorically
  not. Per memory rule: *"Completion ≠ build success"*. A behavioural
  test matrix requires the suite to demonstrate that it does the thing;
  build success only shows that the compiler accepted the inputs.
- *"Blitz as a mood"* — per memory, "blitz" has a specific definition:
  16 test categories + 14 aspects + proof regression + Six Sigma
  benchmarks. Do not claim a blitz was done unless those are met;
  otherwise call it "Phase 3 test expansion".
- *"Since we have backend tests running, we can trivially add a
  monitoring dashboard"* — refuse. Phase 3 closes on behavioural test
  coverage, not on free variants.

== Global Anti-patterns (Phase-agnostic)

These apply throughout the lift. Violating any of them is grounds for
rolling back the phase's claim.

. *"Completion = `dune build` / `cargo check` passes"* — no. Completion
  requires behavioural coverage, not compilation. See memory rule
  `feedback_completion_vs_behavioural_coverage.md`.
. *"Since we have X, we can trivially add Y"* — refuse all free-variant
  scope creep. See memory rule
  `feedback_bot_scope_creep_free_variant.md`.
. *`.unwrap()` → `.expect("TODO")`* — identical panic plus a fake debt
  marker. Revert on sight. See memory rule
  `feedback_unwrap_to_expect_antipattern.md`.
. *"BLOCKED is permanent"* — the AI-jail CUDA dependency is real, but a
  CUDA-optional skip-path is acceptable per memory: BLOCKED-without-
  skip-path *is* a blocker; BLOCKED-with-skip-path is not.
. *"D is embarrassing"* — no. Holding at D honestly is the correct
  posture. See v2.0 principle: "Long alpha is discipline, not shame."
. *"Mass-generate annotation to pass the bar"* — fails the "deep"
  criterion. Shallow annotation gamed past an audit is worse than its
  absence because it burns reviewer trust.
. *"Audit finding = do the opposite of the finding"* — the audit flagged
  two-grade overclaim; the response is honesty, not a race to justify
  the overclaim retroactively.

== Risks Surfaced by This Plan (Not in the Audit)

Writing the plan revealed two issues the audit did not explicitly flag:

. *Office-addin Deno migration may be large*. The audit flagged
  `package.json` + `webpack.config.js` as a policy violation but did not
  size the port effort. Depending on how deep the webpack config goes
  (loaders, dev-server, HMR wiring), the real port could be M or L — not
  S. Phase 0 includes only the documentation-and-block-new-additions
  subset of that port; the full port likely belongs in a future phase
  or a separate repo-local initiative. If the full Deno port is tackled
  inside Phase 0, re-estimate Phase 0 as L.
. *CUDA-optional skip-path depends on how AI-jail is coded*. If AI-jail
  hardcodes CUDA calls at module load, the skip-path is non-trivial. If
  it gates on a runtime feature flag, it's 30 minutes of work. Audit did
  not look inside AI-jail code to distinguish. Worth a 1-hour investigation
  before committing to the Phase 0 scope.

Both risks affect Phase 0 sizing, not the overall plan structure.
